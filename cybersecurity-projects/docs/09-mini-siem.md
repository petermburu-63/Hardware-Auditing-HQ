# Project 9: Mini SIEM / Log Correlation Engine

**Side:** Defense · **Difficulty:** High · **Language:** Python

## What is this, in plain English?

A **SIEM** (Security Information and Event Management system) is the central nervous system of a real security team: it pulls in logs from *every* machine, firewall, and application across an organization, and looks for patterns that no single log alone would reveal. One failed login on one server is nothing. But one failed login on ten different servers within 30 seconds, all from the same external IP, is a coordinated attack — and you'd only ever see that by looking across all the logs *together*, which is exactly what a SIEM does.

## Why it matters

- Real SIEMs (Splunk, Elastic Security, Microsoft Sentinel) are the backbone tool of every Security Operations Center (SOC) job on the planet — this is the single most directly job-relevant project on this list.
- It teaches **correlation**, which is the actual hard, interesting problem in defensive security: not just "did something bad happen" but "do these ten separate, individually-boring events together mean something bad is happening."
- It naturally pulls together everything from Projects 2, 4, and 7 — this is the project where all your other logs finally have somewhere to go.

## How it actually works

1. **Ingest**: collect logs from multiple sources into one place — could be your HIDS alerts (Project 4), your FIM alerts (Project 7), your packet sniffer's flagged events (Project 2), auth logs from multiple VMs, etc. Normalize them into one common format (timestamp, source host, event type, details) since every source formats its logs differently.
2. **Store**: put normalized events into a simple database (SQLite is plenty to start) or a proper time-series/log store if you want to go further (Elasticsearch is the industry-standard open-source choice).
3. **Correlate**: write rules that span *multiple* events, not just one:
   - Same source IP failing login on 3+ different hosts within 5 minutes → possible credential-stuffing/lateral movement
   - A file integrity alert on Host A followed by a new outbound connection from Host A within 60 seconds → possible malware just got planted and is phoning home
   - A spike in failed logins followed immediately by one success → possible successful brute-force
4. **Score and prioritize**: not every alert matters equally — assign severity so a human reviewing this isn't drowning in noise (alert fatigue is a real, huge problem in actual SOCs).
5. **Visualize/report**: a simple dashboard (even a basic web page showing recent alerts, top offending IPs, a timeline) makes this dramatically more usable than a scrolling terminal log.

## Build it yourself (core pieces)

- SQLite + Python is enough to prototype the whole thing — don't reach for Elasticsearch until the simple version works.
- Design your common event format first (a Python dict/JSON with consistent field names) — this is the unglamorous but most important design decision in the whole project.
- Start with just one correlation rule (the multi-host failed-login one above) and get it working end-to-end before adding more rules.
- A simple Flask dashboard showing "alerts in the last 24 hours" is a great visible deliverable to show off.

## Where to practice safely

- Entirely safe — you're writing a log analysis tool, not attacking anything. Feed it logs from your own lab VMs (ideally generated by your own tools from Projects 2/4/7) to test it realistically.
